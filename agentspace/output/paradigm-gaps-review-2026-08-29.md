# 范式能力缺口清单评审（2026-08-29）

对 `prompt/output/interaqt-paradigm-gaps-2026-08-29.md`（GAP-1 至 GAP-12）逐条评审：判定该缺口应由框架解决还是由应用层解决，并对属于框架的部分给出建议方案。

- **基准**：主干 `94a9194`，版本 4.10.0。来源清单以 4.8 的公开行为为基准，其中数条已被 4.9.0 / 4.10.0 部分或全部关闭。
- **方法**：每条先核实源码事实（附文件与行号），再判定归属，最后给方案。凡来源清单的事实陈述与主干不符者，明确指出。
- **术语**：本文用「值匹配 Relation」（key-join relation）指一种由两端键列取值决定连边、无需物理链接行的关系声明；用「分区折叠」（partition fold）指「按某个键把多行归约成一个值或一行」的计算形态。两者均为本文提出的建议概念，当前框架不存在。

跨条目收敛（本次评审的主要发现）：

1. **GAP-3 / GAP-4a / GAP-9 是同一个缺口**——「按键把多行归约到一处」。当宿主记录存在而只缺 Relation 时，一个值匹配 Relation 同时解决三者，且复用现有聚合增量引擎与成员资格差分机制，不引入第二套计算路径。
2. **GAP-5 / GAP-8（超时）/ RealTime 是同一个缺口**——时间驱动重算调度器。`RealTime` 已经持久化 `nextRecomputeTime`，但没有任何消费者，其声明期错误信息自陈 "Time-based rescheduling is not implemented yet"（`src/runtime/computations/RealTime.ts:127-138`）。这是当前唯一同时挡住三条需求的缺失原语。
3. **GAP-6 / GAP-12 是同一个机制**——声明命令式写面，并把「没有任何派生依赖它」从人工审计升级为声明期/启动期不变式。
4. **GAP-7 与 GAP-11 相互约束**——若框架提供基于事件日志的跨进程投递，则日志修剪必须以最慢消费游标为下界。两条若分别设计，会造出「消费者尚未读到的事件已被保留策略删除」这一新的静默失败。
5. **索引声明缺失是多条性能条目的公共底座**（GAP-4c、GAP-9、GAP-10）。框架完全拥有 DDL，却没有声明非唯一二级索引的能力：`Setup.ts` 的建表语句不含任何索引，`Entity.constraints` 只接受 `UniqueConstraint`（`src/core/Entity.ts:496-501`），实际创建的索引全部是唯一索引（`SchemaDialect.ts:143-163`、`MonoSystem.ts:1076-1085`），关系外键列亦无索引。对一个声明式框架而言这是结构性欠账。

## 2. 逐条评审

### GAP-1 身份自举与按自然键的幂等创建 —— 大部分已关闭

**事实核实。** 来源清单以 4.8 为基准，其结论「唯一约束冲突之后的裁决只能由应用层手写」在主干上不再成立。

- 4.10.0 交付 `Entity.identity`（`src/core/Entity.ts:52-53`，声明期校验 `normalizeEntityIdentity` 于 `:280-388`）。写路径汇合在 `CreationExecutor.createIdentityRecord`（`src/storage/erstorage/CreationExecutor.ts:848-1020`）：`INSERT ... ON CONFLICT (identity 列) DO NOTHING`，冲突方在同一事务内按键查回既有行并返回 `{ kind: 'observed', row }`（`:966-1011`）。冲突方拿到胜出方的存储行、不报错、不发 create 事件。这正是清单要求的「收敛」策略，且并发正确性在 PostgreSQL READ COMMITTED 下即成立，无需 SERIALIZABLE 或重试。
- 另一半「失败」策略由 `UniqueConstraint` 提供（重复是类型化的 `ConstraintViolationError` 并回滚），两者在同一属性集上互斥、声明期报错（`Entity.ts:378-387`）。也就是说，清单要求的「声明自然键与冲突策略（收敛 / 失败）」两个分支在主干上都已有一等表达。
- 关于「匿名 / 系统事件源」：清单称「框架没有面向匿名或系统来源的事件原语」，这一条**不准确**。核心层 `EventSource.create` 的参数类型完全由调用方决定，不含 user 概念，事件实体也由调用方自建（`src/core/EventSource.ts:198-222`，`:80` 的注释即称其为 anonymous EventSource）。`Controller.dispatch` 入口不做任何 user 校验（校验只有四项：eventSource 非空、嵌套 dispatch、非业务事务内 dispatch、业务事务已中止）；`USER_ENTITY` 常量在 `src/` 内无任何校验消费。内建 `Interaction` 把 `user` 声明为必填只是其自身的类型契约。

**判定。** 能力上已关闭；剩下的是**文档缺口**——使用指南把 `Interaction` 当作事件的唯一正统入口，导致「注册、验证码签发、合作方开通」这类无主体入口的作者找不到正规写法，只好退回手写存储原语。这是框架应当解决的问题，但解决方式是文档与示例，不是新原语。

**建议。**

1. 在使用指南中把「系统 / 匿名事件源」写成一条正式配方：自建事件实体 + 核心 `EventSource.create` + 自己的 `admit`，并说明它与 `Interaction` 的分工（后者的契约包含 user 与 payload 校验）。同时明确：对 `Interaction` 而言拦住匿名调用的只有用户自己写的 Condition，框架层没有 user 闸门——这一点目前未成文，容易被误当作有保障。
2. 补齐两处能力残余的显式说明（当前只能从源码读出）：`Relation` 的创建面没有 `identity` 参数，filtered / merged 实体不得声明 identity（`Entity.ts:301-310`）；MySQL 在 setup 期直接 fail-fast（`Setup.ts:746-754`）。
3. 唯一可考虑的小幅 API 补强：观察路径下调用方需要「effects 中有无 create 事件 + 提交后按键查询」两步才能判别实插与观察。若实践反馈这一步骤易错，可在 `DispatchResponse` 上补一个只读的解析结果通道；但这会新增第三条响应通道，与已定的结果代数冲突，**不建议在没有实测痛点前先做**。

### GAP-2 存量列升级为派生列 —— 框架应解决，但需重新界定范围

**事实核实。** 清单描述准确：属性新挂 computation 在迁移引擎中是显式的一等机制 `computation-takeover`，决策合同强制 `oldDataStrategy: "discard-and-rebuild"`（`src/runtime/migration.ts:1975-1977`），执行时不仅用计算结果覆盖存量值，还把旧值从计算输入中剥除（`stripPropertyFromInput`，`:3747-3752`），并强制合成 mutation 事件以驱动下游重建（`:3277-3284`）。当前不存在收养路径；最接近的两个机制是已有计算的 `possibly-changed` 决策为 `unchanged`（不进重建计划、存量输出原样保留，`:2126-2141`），以及反方向的计算移除（computed → fact，天然收养，`:1736-1746`）。StateMachine 的接管被整体禁止，理由是缺少状态重建处理器（`:2018-2020`）。

**判定。** 属于框架，但清单建议的「computation 的收养模式：接管属性时把既有存量值视为初始状态」若不加限制，会破坏范式的基本契约。必须区分两个计算族：

- **数据驱动聚合**（Count / Summation / Average / Every / Any / WeightedSummation）：这一族的输入集合当下完全可观测，且框架为每一项贡献维护绑定状态（`aggregationTemplate.ts` 的 `itemState`）。若只把总量收养为初始值而不重建逐项贡献，之后删除任一成员时会用一个从未累加过的贡献去做减法，聚合值静默出错，计数类还会撞上负值守卫直接崩溃。也就是说，**对这一族「收养」在语义上不成立**——而且不需要：输入还在，重算既正确又便宜。现状 `discard-and-rebuild` 是正确答案。
- **事件驱动计算**（属性级 StateMachine、`eventDeps` 形态的 Transform）：这一族的值是对**历史事件流的折叠**，而历史事件可能已经不可重放（事件日志被修剪，或该事实本就来自外部系统、从未以事件形式进入过框架）。此时「把存量值当作折叠到切换点的状态、此后的事件在其上继续折叠」是事件溯源里标准的检查点（checkpoint / snapshot）语义，定义清晰、可测。清单举的例子（媒体文件时长——由外部探测得到的事实）正属于这一族。

**建议。** 在既有迁移决策合同上增加一个受限的收养策略，而不是新增 computation 声明面：

1. 新增 `oldDataStrategy: "adopt-as-checkpoint"`，**仅对事件驱动计算合法**；数据驱动聚合声明该策略时在迁移审阅期 fail-fast，错误信息说明「输入集合可观测，收养会使逐项贡献状态与聚合值失步，请使用 discard-and-rebuild」。
2. 收养的实质是初始化绑定状态，因此它天然复用现有的 `event-rebuild-handler` 决策机构：把该处理器的语义从「重建状态」扩展为「由存量值推导初始绑定状态」。这同时解开了 StateMachine 接管当前被整体禁止的死结——禁止的原因正是缺这个处理器。
3. 配套一个**可选执行**的一致性校验步（清单也提到）：对可重放的子集，回放派生函数并与存量值比对，报告不一致的行数与样例 id。定位为迁移前的审阅辅助，不作为收养的前置条件（否则不可重放的场景永远过不了）。
4. 迁移签名与审阅报告需体现收养：收养后该属性的值**不再是当前输入的纯函数**，后续任何一次全量重建都会改变它。这一后果必须写进决策记录与文档，否则会在若干轮之后以「重建后数据变了」的形式二次爆发。

### GAP-3 按属性分组的聚合 —— 框架应解决，价值最高，但方案不应是 GROUP BY 计算

**事实核实。** 清单描述准确。六个内置聚合只有两种寻址形态：沿一段 Relation 聚合到宿主属性（`PropertyRelationAggregationHandle`，`aggregationTemplate.ts:266-342`），或对整表做全局聚合并落 `_Dictionary_`（`GlobalRecordsAggregationHandle`，`:139-259`）。`record` 与 `property` 互斥二选一，无多级路径形态（`klassValidation.ts:39-53`）。按属性值分组的聚合不存在，也无雏形；唯一的按维度分区原语是 `ScopedSequence.scope`，只做分区内序号分配。

**判定。** 属于框架，同意「价值最高」的排序。但清单建议的「一等的分组聚合 computation：声明源实体、分组属性、聚合函数与增量维护策略」有一个结构性问题：**结果放在哪里**。三个候选都不好：落 `_Dictionary_` 是把无界的键值映射塞进单行 JSON；落一个派生实体则等于让框架为它发现的每个分组自行造行，与「行由 Transform 铸造」的既有契约冲突；落宿主属性——那正是现有 property 级聚合，只是连接方式从 Relation 换成了属性值。

第三个候选指向真正的答案。在响应式 ER 模型里，分组键**本该是一条记录**，分组本该是一条 Relation：账户是记录、交易指向账户，则账户上的 `Summation` 就是 `SUM(...) GROUP BY account`。应用做不到这一点的原因是 GAP-9（只有业务键字符串、没有 Relation），而 GAP-9 又因为缺分组聚合与高效按键连接而回报不足——清单自己识别出了这个循环。**打破循环的最小改动是让 Relation 可以由属性值定义，而不是新增一种聚合。**

**建议：值匹配 Relation（key-join relation）。**

```typescript
const TransactionAccount = Relation.create({
  source: Transaction, sourceProperty: 'account',
  target: Account,     targetProperty: 'transactions',
  type: 'n:1',
  // 连边由两端键列的取值决定，无物理链接行
  match: { sourceKey: 'accountId', targetKey: 'id' },
})
```

声明之后，`SUM(amount) GROUP BY accountId` 就是账户上的普通属性：

```typescript
Property.create({
  name: 'balance',
  computation: Summation.create({ property: 'transactions', attributeQuery: ['amount'] }),
})
```

这个方案之所以值得优先：

1. **零新增计算类型**。六个聚合、增量模板、逐项贡献状态、竞态防御、迁移重建、既有测试面全部原样复用。清单担心的「框架不保证人工枚举的完整性」由此彻底消失——完整性由聚合引擎的事件路由保证，而不是由状态机转移表的人工同步保证。
2. **两块难做的机制框架都已经有**。其一，成员资格的写时差分：`FilteredEntityManager` 已经在做「变更前采集快照 → 变更后重新求值谓词 → 差异即成员资格 create/delete 事件，全部在写事务内」（`FilteredEntityManager.ts:103-112`）。值匹配 Relation 的连边条件就是一个作用在一对行上的谓词，`Transaction.accountId` 由 A 改为 B 时需要发出「A—T 连边删除、B—T 连边新建」两个事件，形状与 filtered relation 的成员资格差分完全一致。其二，按连边事件驱动的增量聚合已经存在（`aggregationTemplate.ts:421-539`）。
3. **物理足迹为零**。`x:1` 的值匹配关系可编译成 `source.accountId = target.id` 的连接，不需要链接表，也不需要数据回填——这正是 GAP-9 求的东西（见该条）。
4. **与 4.10.0 的 `Entity.identity` 天然咬合**。要求目标端键必须是逻辑 `id` 或已声明的 `identity`，则唯一性（`n:1` 良构的前提）与索引（连接效率）由已有机制免费提供。这是一次真正的能力复用，而不是并列新增。

设计需要明确裁定的点：

- **基数范围**：建议先只支持目标端为 `id` / `identity` 的 `x:1`。按值的 `n:n`（两端共享某个标签值）语义与增量代价都显著更复杂，不应进入第一版。
- **悬挂键**：目标行尚不存在时无连边；目标行创建后连边出现，成员资格 create 事件驱动聚合增量。这是良定义的，且对「父行迟到」是有用行为。引用完整性因此成为可声明的约束，而非隐含不变式——需要显式文档化，否则会被误当作框架保证。
- **键列可变性**：键列可改（改则连边迁移），但需在文档中写清这会同时改变两侧的聚合值与查询路径。
- **不可与 `identity` 混淆**：identity 是「这一行的自然键」，值匹配 Relation 是「这两行按键相连」。文档需并置说明，避免第三种身份概念出现。

**关于确实没有宿主记录的分组**（例如「按 status 枚举分桶计数」）：这一形态今天已经可以表达——每个桶一个 filtered entity + Count，或者按 ER 建模的常规做法把枚举建成查找实体并建行。这类退化情形不需要新原语。真正难受的是租户 / 账户 / 工作区这一类，而那里宿主记录本来就存在、缺的只是 Relation。这加强了上面的方案选择。

### GAP-4 物化视图 / 可重建投影 —— 拆成三块，分别裁定；反对引入投影原语

清单把三件事打包成一个「物化视图原语」的诉求。三件事的归属与代价差异很大，必须分开。

#### 4a 从每条修订链折叠出当前生效版本 —— 框架，与 GAP-3 同族

**事实。** 数据驱动 Transform 是「每条源记录映射到 N 条派生记录」，由 `(sourceRecordId, transformIndex)` 绑定状态维护映射并 diff 出 update / insert / delete（`src/runtime/computations/Transform.ts:139-227`）。它无法表达「N 条源记录归约为 1 条输出」。也就是说，**Transform 是按源行的映射，不是按键的折叠**——这与 GAP-3 缺的是同一个形状，只是输出从标量变成了一行记录。

**建议。** 在 GAP-3 的值匹配 Relation 之上，修订链折叠的正统表达是：`Chain` 实体（每个业务对象一行，由首个修订的 Transform 铸造）+ 值匹配 Relation `Chain—Revision`（按链键）+ `Chain` 上的属性级聚合给出当前生效版本。此处暴露出内置聚合族的一个真实空缺：**没有 `Latest` / argmax 形态的聚合**（六个聚合只有计数、求和、均值、全称、存在、加权和）。目前只能用属性级 `Custom` + 关系 dataDep 手写。建议：

1. 补一个「按排序键取极值项」的内置聚合（形如 `Latest.create({ property, orderBy, attributeQuery })`），其增量语义在「新项进入」时便宜、在「当前极值项退出」时退化为分区重算。这是聚合族里被反复手写的形状，值得一等化。
2. 在此之前，把「属性级 Custom + 关系 dataDep 实现 argmax」写成官方配方，避免每个应用各自发明。

#### 4b 一次读取内部的快照一致性 —— 框架，但接近已有能力

**事实。** 应用手写了「读前读后各取一次单调递增的版本水位，两次一致才确认未撕裂」。框架侧其实已有 `storage.runInTransaction` 并支持隔离级别；在 PostgreSQL 上以 REPEATABLE READ 执行一组读即得到一致快照。缺的不是机制，而是**没有把它作为读一致性的正规入口呈现出来**：现有文档与守卫都围绕写路径（裸 `runInTransaction` 内 `dispatch` 会抛 `DISPATCH_IN_NON_BT_TRANSACTION`），读路径的一致性没有对应叙述。

**建议。** 提供一个只读快照读入口（例如 `storage.runInSnapshot(callback)`，内部为只读 + 快照隔离，不允许写、不允许 dispatch），并在使用指南的查询章节把它确立为「一次读取内部快照一致性」的官方答案。改动面小，且直接消除应用手写水位双读这一类绕行。

#### 4c 维护「当前活动事实」的指针索引 —— 归结为索引声明缺失

**事实。** 「当前活动」这件事今天就能声明：新修订创建时，由 StateMachine 把前一修订推进为 superseded（`StateTransfer.trigger` 可匹配任意记录的 mutation 事件，`computeTarget` 定位前一修订），再用 filtered entity `ActiveFact` 声明谓词子集。filtered entity 的读是谓词下推到 base 物理表的实时求值（`MatchExp.ts:104-116`），不存在成员标记脱同步问题。所以清单描述的「每次读取都要对全部历史事实做一次折叠」并非范式缺陷——**它是索引缺失**：谓词下推之后仍然全表扫描，因为框架不提供任何非唯一二级索引的声明能力。

**建议。** 增加索引声明（见 §1 收敛点 5），例如 `Entity.indexes: [{ properties: ['isCurrent', 'chainKey'], where?: ... }]`，纳入迁移逻辑签名与 additive DDL。这是纯加性改动、无语义风险，且同时服务 GAP-9 与 GAP-10。

#### 对「物化视图原语 + 显式排除在响应式依赖图之外」的反对意见

清单建议「投影显式排除在响应式依赖图之外」。**不建议采纳。** 理由：这等于在框架内并列出第二套派生引擎，它有自己的失效协议、自己的滞后语义、自己的重建入口，而与主依赖图之间没有一致性契约。同仓的 `prompt/dual-state-sources.md`（FR-DS-01）正在要求关闭的恰恰是「同一事实两份持久表示、读路径无合同」这一形态；引入一个官方的「图外投影」会把该问题制度化。上面 4a/4b/4c 的分解表明，这三项需求可以全部落在既有依赖图内，不需要开这个口子。

另外，清单称「computation 无法表达从提交后快照取输入」，这一条**不准确**：异步计算（`Custom` + `asyncReturn`）就是在提交后由外部工作者读取状态、经 `handleAsyncReturn` 在独立事务内落库（`Scheduler.ts:1291-1378`），并有 `freshnessKey` 分区与陈旧结果作废机制。若确有「必须以提交后快照为输入」的投影，异步计算是现成的正规通道。

### GAP-5 读触发的惰性刷新 —— 主要属应用层；框架的真实缺口是时间驱动调度器

**事实。** 整个计算体系是纯写驱动，不存在任何读触发刷新机制。同时，`RealTime` 计算把 `nextRecomputeTime` 持久化进绑定状态（`RealTime.ts:75-80, 148-153`），但 Scheduler 对它零消费；属性级 `RealTime` 在既无 `attributeQuery` 也无 `dataDeps` 时声明期直接拒绝，错误信息自陈时间驱动重算尚未实现（`:127-138`）。

**判定。** 「因读取而触发一轮外部拉取」不应由框架承担：它使读变成写（GET 产生事务与写入）、使读延迟依赖外部服务商、并且并发合并（single-flight）在多副本下需要跨进程租约。这三项都与框架的核心承诺（派生数据相对已提交输入始终是最新的）以及「显式控制」原则相抵。读路径的缓存策略属于应用的 HTTP 处理层。

但清单场景里有一段框架侧的真实缺口。应用自己就写明「权威收敛仍由后台重试机制负责」——也就是说，声明式的表达是「这个值超过 N 秒即视为过期，应被重算」，即**时间驱动重算**。这正是框架承认但未实现的那一项。若时间调度器存在，该需求变成：声明一个带过期窗口的异步 `Custom` 计算，调度器到期入队刷新任务；并发合并由现有的 `freshnessKey` 分区与 `invalidateUnappliedAsyncTasks` 承担（`Scheduler.ts:1380-1419`）；失败回退即「保留上一次结果 + 任务留在待重试态」。读路径于是只需读值与 `lastRefreshedAt`——正是应用实际返回的东西。

**建议。**

1. 实现时间驱动重算调度器，消费已经在持久化的 `nextRecomputeTime`。这同时解开 `RealTime` 的自陈 TODO 与 GAP-8 的超时需求（见 §1 收敛点 2）。设计要点：调度是**维护步**而非后台线程隐式启动（与 `maintainEntityRetention` 的显式风格一致），提供 `controller.runDueRecomputations()` 之类的入口，由部署方决定谁来驱动（cron、常驻 worker 均可）；多副本下到期任务需按记录取锁，避免重复执行。
2. 若日后确实要承认读触发刷新，最小且不违背显式控制的形态是一个**非权威的维护调用**（例如 `controller.ensureFresh(...)`），由应用在自己的读处理器里显式调用，而不是给 `storage.find` 挂隐式钩子。不建议在时间调度器落地前先做这一项。

### GAP-6 观测型属性与事件写放大 —— 框架应解决

**事实。** 清单描述准确且代价可核实：每次 applied dispatch 无条件写一条事件记录，这是管线的固定步骤，不可关闭（`Controller.ts:1670-1674`）。因此维护一个 `lastUsedAt` 的正统路径至少产生两行持久写入。另一方面，框架内部**已经有**「写而不发事件」的机制：`updateInternal` 的自身 update 事件被 `shouldDispatch` 过滤，不进回调也不进 effects（`System.ts:247-252`，`MonoSystem.ts:1982-1984`）。也就是说所需机制存在，只是没有对应的声明面。

**判定。** 属于框架。应用的绕行（节流直写 + 静态检查保证无 computation 依赖该列）并不违法——`storage.update` 是合法 API——而是**不可治理**：框架无法检查「没有任何派生依赖它」这个不变式，只能靠应用自建审计。这与 GAP-12 是同一个形状。

**建议。** 引入观测型属性声明，并把它同时作为 GAP-12 的一个特例：

1. `Property.create({ name: 'lastUsedAt', observational: true })`。语义：(a) 该属性的写入不产生 mutation 事件，也不产生交互事件记录；(b) 该属性可经声明允许的命令式边界直写。
2. **声明期 / 启动期 fail-fast**（这是本条最主要的价值）：任何 computation 的 dataDep / eventDep 不得引用该属性；filtered entity 的谓词不得引用；StateMachine trigger 的 `keys` 不得包含。把应用今天用静态检查手工维护的登记，变成框架的受检不变式。
3. **不建议把节流 / 合并写入纳入框架**。写速率是部署策略，且框架侧的去抖会引入「我的写是否已持久化」的语义歧义。收益的三分之二（免交互事件行、免事件扇出、受检的无依赖）不依赖节流即可获得。
4. 文档需明确该属性在迁移与审计中的地位：它是事实列、不参与重建、不出现在事件轨迹里，因此不可用于任何需要审计追溯的用途。

### GAP-7 跨进程副作用投递 —— 拆两块

**事实。** 全 `src/` 搜索 outbox / subscribe / poll 零命中：没有发件箱表、没有持久化订阅、没有轮询器。`RecordMutationSideEffect` 注册表是 Controller 实例级（`Controller.ts:517-521`），执行时机为提交后、进程内、逐项 await，失败逐项捕获为 `SideEffectError` 且不重试、不持久化（`:1772-1813`）。4.9.0 提供的是可观测性（`postCommitPhase` / `isPostCommitPhaseComplete`）与手动恢复（`rerunCreateMutationSideEffects` / `rerunPostCommit`），不是可靠投递。

需要修正清单的一处措辞：「框架隐含单进程假设」只对**阶段 P（提交后副作用）**成立。计算是存储状态的确定性函数、在执行写入的那个进程内运行，多进程本身没有问题；Activity 状态也完全持久化在 `_Activity_` 且跨进程可恢复水合（`ActivityCall.ts:426-437`）。

**判定与建议，分两块。**

**(a) 消费者与进程的声明式注册表 —— 属于框架，且应当优先做。** 清单描述的失败形态是：配置错误 → 事件被标记为已投递、目标进程根本没有注册消费者 → 静默失败。对一个把 fail-fast 作为质量教义的框架来说，这是一个 fail-open 的洞，而堵它很便宜：

1. 在 `RecordMutationSideEffect` 上增加宿主角色声明（例如 `host: 'http' | 'worker' | ...`，取值集合由应用声明），并在 `Controller` 构造 / setup 期断言：本进程声明的角色所应承载的副作用全部已注册；全体角色合起来覆盖所有已声明的义务。缺失即启动失败，附缺失清单。
2. 这条不需要任何投递机制先落地即可独立交付，且它把「哪个消费者必须部署在哪个进程」从文档约定变成启动期不变式。

**(b) 框架级事件外发与订阅 —— 已有明确非目标，若要做需精确界定最小形态。** `prompt/post-commit-side-effect-delivery-guarantees.md` §6 已经裁定「框架不做出站调度：不内置重试 / 退避 / outbox / 死信调度」。这个裁定是站得住的（投递编排是基础设施，各应用差异极大），维持。若日后决定提供跨进程投递，需要注意一个关键的实现约束：

- **交互事件日志已经是事务性发件箱的写侧**：`_Interaction_` 行在事实事务内写入、append-only、按 id 有序。基于它做「消费组游标 + 至少一次投递 + 应用侧幂等消费」是小改动，且 4.9.0 的 rerun API 已经提供了执行侧的大半。
- **但 mutation 事件流没有持久化**。`RecordMutationSideEffect` 匹配的是记录变更事件，而这些事件只存在于内存与 `result.effects`。要跨进程投递 mutation 事件就必须引入一份变更日志（mutation journal），那是重量级改动，且与派生状态引擎职责重叠。建议明确：跨进程投递若做，**只覆盖已提交的交互事件**，不承诺 mutation 事件；mutation 副作用保持进程内语义并由 (a) 的注册表保证装配正确。
- **与 GAP-11 的耦合必须在同一份设计里裁定**：日志修剪不得越过最慢消费游标，否则会造出新的静默失败。

### GAP-8 长时流程编排 —— 框架决策，但清单给的两个选项都不最优

**事实。** 逐项核实与清单一致：Activity 支持 `any` / `every` / `race` 三种组合与嵌套子活动，每层是严格线性序列（每节点单一 `next`，同源第二条 transfer 直接报错），Gateway 类型存在但运行期拒绝，分支只能用 ActivityGroup 表达。失败重试与退避、超时控制、活动级外部回调、补偿（saga）**均无**；按操作标识的幂等重放**有**（`_DispatchIdempotency_`，活动包装器转发 idempotency 并支持 `scope: 'interaction'`）。4.5.0–4.10.0 无任何 activity 条目，4.x 的 activity 改动全是 fail-fast 守卫与生成式测试。

清单未记入的一项优点：Activity 状态全在数据库、进程内不持有运行态、跨进程与重启可恢复，且定义漂移会抛 `ActivityStateError` 而非静默错乱（`ActivityCall.ts:135-178`）。

**判定。** 同意「悬置是最不利状态」。但两个选项都不建议直接采纳：

- **演进为持久执行引擎**意味着要建定时器、工作者池、租约、调度守护——在一个数据框架内部再造一个工作流运行时，带来第二套失败模式。而且顺序是反的：框架目前连 `RealTime` 的定时重算都没有（GAP-5），在没有调度器之前先做持久执行是本末倒置。
- **正式废弃**会丢掉 Activity 真正提供的东西。Activity 今天实际是什么，如实描述：**对交互顺序的声明式准入约束**（「这个交互只在图上的这个位置可被接纳」），带持久化、CAS 保护、崩溃可恢复的状态。这是有价值的能力，而且不是编排引擎做的事。它并非「代差」，而是被当作工作流来宣传的另一种东西。

**建议：第三条路。**

1. **收缩契约声明**。在文档、README 与错误信息中把 Activity 重新定义为「交互顺序的准入约束」，明确它不提供重试、超时、补偿、外部回调，并指出这些需求的正规归属。抽象的表达力与其宣称一致之后，「抽象存在但无人能用」这一状态即消解。
2. **公布外置编排的集成契约**（清单选项 2 里真正有价值的部分，且与选项 1 不冲突）：事件如何出（GAP-7 的消费游标）；步骤如何入（`dispatch` + `idempotency`，`outcome: 'applied' | 'replayed'` 即步骤级幂等回执）；事务边界如何划（一次 dispatch = 一步 = 一次原子事实提交；需要跨步共享原子边界时用 `runInBusinessTransaction` 并顺序 dispatch）；提交后义务的完成判别与恢复（`isPostCommitPhaseComplete` + rerun API）。这些机制**全部已存在**，缺的只是把它们组装成一份成文契约。
3. **不建议引入 saga / 补偿原语**。在响应式模型里补偿就是一个声明出来的逆向交互，框架已具备表达它的全部要素；新增补偿概念会与「交互是数据变化的唯一入口」形成第二套语义。
4. **唯一值得补的原语是时间驱动调度器**（与 GAP-5 同一件事）。有了它，「超时」成为一个带时间触发条件的 StateTransfer：状态停留超过 T 则转移。这是把清单里唯一无法用现有要素表达的需求，用一个通用原语关闭，而不是引入一个工作流子系统。

### GAP-9 Relation 采用激励不足 —— 观察成立，解除依赖 GAP-3

**事实。** 与清单一致：`MatchExp` 的 key 必须逐段解析为已声明的 Relation 段（`MatchExp.ts:210-299`），`exist` 子查询与列对列比较同样只能沿关系路径（`:362-387`、`:394-415`）。只有业务键字符串关联的两个实体无法做按值连接，只能应用侧两步查询（先查 A 收键值，再对 B 用 `['in', values]`，且绑定参数有硬上限：SQLite 32766、PG/MySQL 65535，`:417-430`）。

**判定。** 观察成立，而且清单指出的「收益递减循环」是对的。但清单建议的三项里，第 3 项（业务键属性迁移为 Relation 的工具链：生成回填脚本、校验双向一致性）在采纳 GAP-3 的方案后**基本不再需要**——这正是那个方案最有力的地方：

**值匹配 Relation 是对既有列的纯声明，回填成本为零。** 存量模块补 Relation 只需增加一条声明，不动一行数据、不做一次迁移。这直接把采用激励从「回报不足」翻转过来，而不是靠降低回填成本来缓解。

**建议。** 按此顺序推进：

1. 值匹配 Relation（GAP-3 的方案）——同时给出按业务键的高效连接与分组聚合，且零回填。
2. 索引声明（§1 收敛点 5）——值匹配连接的效率前提；目标端要求 `id` / `identity` 时索引已有，源端键列需要可声明索引。
3. 文档层面把「业务键字符串 + 手写查找链」明确列为反模式，并给出「保留原列 + 增加一条值匹配 Relation」的渐进采用配方。**不需要**为主键折叠提供工具链——保留原列即可，这与 `prompt/entity-identity-and-relations.md` §5 的超集发布原则一致。

### GAP-10 权限条件的重复查询开销 —— 框架应解决

**事实。** 与清单一致：条件经 `BoolExp` 组合后短路求值，每个条件的 `content` 各自发起 `storage.findOne`，无记忆化、无预取。唯一的共享是 `AdmissionSnapshot`：求值前从所有原子（含 not 之下）收集声明式 `locks`，按 (recordName, id) 稳定排序去重，经 `storage.atomic.lockRecord/lockRows` 在当前 dispatch 事务上加行锁并一次性取行，seal 后作为 `content` 的第二参数传入（`Interaction.ts:564-755`）。此外 `checkPayload` 对 `isRef` 项的存在性检查也是逐项独立 `findOne`（`:874-887`）。同一 dispatch 内所有条件同处一个事务，可见性一致。

**判定。** 属于框架，而且**收敛点已经存在**——`locks` 的「收集 → 去重 → 批量取 → 密封 → 传入」正是清单选项 2 要的「统一预取后再评估」管线。缺的只是：该声明今天只服务串行化，所以为了共享一次读取而声明它会附带一个不必要的行锁。

**建议。**

1. **把 `Condition.locks` 泛化为声明式读集**，锁强度降为其属性：`reads: [{ recordName, id | match, attributeQuery, lock?: 'none' | 'update' }]`；`locks` 保留为 `lock: 'update'` 的别名以维持兼容。同一 dispatch 内一个条件声明的读被全体条件共享，且不再被迫加锁。既有的排序去重与密封语义（防原子间互相污染）原样复用，不新增概念。
2. **payload 引用项批量预取**：`isRef` 的引用形状在声明面就是已知的，框架无需任何新声明即可把同一实体的全部引用项合并为一次查询，并把结果放进 `AdmissionSnapshot` 供条件读取。**零新增 API、纯收益**，对高频交互直接省下每次调用的固定往返。建议先做这一项。
3. **不建议采纳选项 1（分发级透明记忆化）**。在事务内对任意 `storage` 读做隐式缓存，正是本项目禁止的隐式行为：它会静默改变有意重读的语义（例如条件在取锁后重读以确认），而且缓存失效边界（同一 dispatch 内的写之后是否失效）没有一个不引起意外的默认值。声明式读集把同一收益放在显式声明之下，符合显式控制原则。

### GAP-11 事件日志的生命周期管理 —— 框架应解决，但比清单描述的更窄

**事实核实。** 清单称「框架现有的保留机制只适合一次性令牌这类小型 TTL 实体」，这一条**不准确**。`Entity.retention` 支持 `cap` 模式，带 `retainLatest` + `orderBy` + 可选 `partitionBy` + 可选 `ttl`（先 TTL 后 cap），即「每个分区保留最新 N 条」——正是高增长日志需要的形状（`src/core/Entity.ts:18-43`、`:206-251`）。修剪在独立存储事务内执行、删除走正常 `storage.delete` 并产生 mutation 事件、依赖该实体的计算照常增量更新（`Controller.ts:651-731`）。

真实缺口在**声明通道**，不在执行机构：

- `InteractionEventEntity`（记录名 `_Interaction_`）由框架以固定参数创建、未声明 retention，`Interaction.create` 硬编码 `instance.entity = InteractionEventEntity`（`Interaction.ts:192`），公共 API 无法补声明。而扫描面本身是覆盖它的——事件源的实体会被并入 `controller.entities`（`Controller.ts:494-497`）。所以差的只是一个声明入口。
- `_DispatchIdempotency_` 账本**完全没有清理**：全 `src/` 无对该表的删除，`maintainEntityRetention` 只扫用户实体、内部账本不是 Entity；`createdAt` 已存但无消费者。行永久累积。这一项比交互事件表更紧迫，因为它是纯框架内部记账，任何用户声明都到不了。
- 当前唯一能配置事件表留存的路径是自定义 EventSource + 自建事件实体上声明 `Entity.retention`——这一点未成文。

**判定与建议。**

1. **为内建交互事件表开声明通道**。它是框架拥有的单例，因此走 `ControllerOptions`（例如 `eventRetention: EntityRetention`）比走 `Entity.create` 更合适，surface 也更小。
2. **为幂等账本定义保留策略**。建议由框架给出默认上界（按 `createdAt` 的 TTL）并允许覆盖，纳入现有维护入口。这是当前无声无息增长最快、且用户完全无法干预的一张表。
3. **明确截断契约，而不是只提供钩子**。这里需要纠正清单的一处论断：「事件不可变、永久追加正是范式自身的要求」。范式要求的是**派生状态是其求值时刻输入流的函数**，不是日志永久保留。一旦派生状态已物化、且迁移引擎的重建契约被遵守（`agent/agentspace/knowledge/usage/15-entity-crud-patterns.md:1236-1241` 已记载 identity 实体的全量重建是「本次重建插入序」的集合语义，占有类 Transform 应倾向 `unchanged` 决策），截断日志是正当的。框架的职责是把截断之后**各能力各自失去什么**写成契约：事件重放的边界、Transform 全量重建的产物变化、identity 键回收后可再次登记（`docs/application-key-occupancy/application-key-occupancy.md` §3.5 已记载）、以及若 GAP-7 落地则消费游标构成修剪下界。
4. **分层归档（热 / 冷 / 归档）留给平台**。框架提供保留策略与钩子；把行搬到冷存储、对象存储或分区表是基础设施职责，纳入框架会引入存储后端形态的第二套抽象。

### GAP-12 命令式写边界的可治理性 —— 框架应解决，代价小、价值高

**事实。** 与清单一致：`resolve` 在 dispatch 的可重试事务内执行、`this` 绑定 Controller、可直写 storage（`Controller.ts:1676-1679`；GetAction 的 resolve 本身就是 `storage.find`）。框架对可写实体与属性集合没有任何声明或校验机制（全 `src/` 搜索 writable / allowedEntities / declaredWrites 无相关实现）。

**判定。** 属于框架。清单的观察很关键：应用为多数直写面建立了「注册表即代码」的静态门禁，而唯一的实质违规恰恰出现在一个未登记的缝隙上——这说明纯应用层的黑名单式巡逻必然存在漏网。这正是本仓 bug 修复教义里「把普遍规则提升为受检不变式」的标准适用场景。

**建议。**

1. **在事件源定义处声明写面**：`EventSource.create({ ..., writes: [{ entity: Media, properties: ['duration'] }] })`。
2. **在存储写入汇合点做 fail-closed 校验，而不是在每个回调里自律**。归因机制已经具备：dispatch 已用 `AsyncLocalStorage` 隔离本次调用的上下文（`Controller.ts:1579-1580`），因此「当前这次写入发生在哪个事件源的哪个阶段」在运行期是可得的。一个校验点覆盖 resolve、afterDispatch、postCommit 全部命令式边界——符合「优先在收敛点修复」的原则，而不是逐分支打补丁。
3. **兼容策略采用超集发布**：声明了 `writes` 即选择加入强制模式（未声明的直写报错并附声明建议）；未声明则保持当前行为。可另提供只告警模式辅助迁移。这与 `prompt/entity-identity-and-relations.md` §5 的渐进采用传统一致，不会让既有应用升级即崩。
4. **与 GAP-6 合并设计**：观测型属性就是「一个被声明的命令式写面 + 受检的无派生依赖不变式」。两条若分开设计会得到两套登记概念；合并后是一个机制的两种用法。

## 3. 建议推进顺序

按「改动面 / 风险」与「解锁的条目数」排序：

| 顺序 | 项目 | 关闭的条目 | 改动面 |
|---|---|---|---|
| 1 | 索引声明（`Entity.indexes`） | GAP-4c，GAP-9 前提，GAP-10 部分 | 小（加性 DDL + 迁移签名） |
| 2 | payload 引用项批量预取 | GAP-10 首要部分 | 小（零新增声明面） |
| 3 | 声明式写面 + 观测型属性 | GAP-12、GAP-6 | 中小（一个写入校验点 + 声明期守卫） |
| 4 | 副作用宿主角色注册表 fail-fast | GAP-7(a) | 小（setup 期断言） |
| 5 | 内建事件表与幂等账本的保留声明通道 | GAP-11 主体 | 小（执行机构已存在） |
| 6 | 声明式读集（`locks` 泛化） | GAP-10 其余 | 中小（复用既有预取管线） |
| 7 | **值匹配 Relation** | GAP-3、GAP-9、GAP-4a 前提 | 大（存储编译 + 成员资格差分），价值最高 |
| 8 | 时间驱动重算调度器 | GAP-5、GAP-8 超时、RealTime TODO | 中大（新维护步 + 多副本取锁） |
| 9 | `Latest` / argmax 聚合 | GAP-4a | 中（聚合族新增一员） |
| 10 | 只读快照读入口 | GAP-4b | 小 |
| 11 | 事件驱动计算的检查点收养 | GAP-2 | 中（迁移决策合同扩展） |
| 12 | Activity 契约再声明 + 外置编排集成契约 | GAP-8 决策 | 文档为主 |

第 1–6 项均为小改动且互不依赖，可并行推进；第 7 项是本清单里价值最高的单项，建议独立立项并按本仓的循环任务流程（设计 → 评审 → 实现 → 审计）执行；第 12 项应尽早做，因为「悬置」本身正在持续造成误用。

## 4. 需要更正来源清单的事实陈述

供来源评审方回写：

1. **GAP-1**：按自然键的幂等创建（收敛策略）已由 4.10.0 的 `Entity.identity` 关闭，冲突方在同一事务内拿到胜出方存储行、不报错、不发 create 事件；失败策略由 `UniqueConstraint` 提供。「冲突裁决仍是空白」不再成立。
2. **GAP-1**：面向匿名 / 系统来源的事件原语**已存在**——核心 `EventSource.create` 不含 user 概念，`dispatch` 入口不校验 user。这是文档缺口而非能力缺口。
3. **GAP-4**：「computation 无法表达从提交后快照取输入」不准确——异步计算（`Custom` + `asyncReturn`）在提交后的独立事务内落库，是现成通道。
4. **GAP-7**：「框架隐含单进程假设」应收窄为「提交后副作用（阶段 P）是进程内的」。计算与 Activity 状态均跨进程可恢复。
5. **GAP-11**：`Entity.retention` 支持 `cap` + `partitionBy` + `orderBy`，即「每分区保留最新 N 条」，并非只适合小型 TTL 实体。真实缺口是内建交互事件表与幂等账本没有声明通道。
6. **GAP-11**：「事件不可变、永久追加是范式自身的要求」应修正为「范式要求派生状态是其求值时刻输入流的函数」。日志截断在重建契约被遵守的前提下是正当的，框架欠的是截断契约的成文化。
