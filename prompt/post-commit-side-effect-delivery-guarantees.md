# 提交后副作用的交付保证：失败可见性与可重执行性

> 面向 interaqt 框架本身的需求摘要。核心问题：**dispatch 把"事实提交"作为唯一的一等原子单位，但大量应用语义挂在提交后副作用上，而这个挂点没有配套的完成语义**——失败不是一等结果、执行不可重入、去重路径把它短路成假成功。
>
> 不绑定任何具体应用仓库。文中场景仅为通用动机说明。与 `prompt/remaining-framework-gaps-seq-idem-retention.md` 的 FR-IDEM-01（首次/回放判别，已以 `outcome: 'applied' | 'replayed'` 交付）相邻而不同：那条解决"事实是否首次生效"，本文解决"提交后义务是否完成、能否完成"。

## 1. 背景：dispatch 的两阶段语义

`Controller.dispatch` 实际是两个阶段（`src/runtime/Controller.ts`）：

**阶段 A —— 事实事务**（`runDispatchAttemptBody`，:1469-1604，在 `runInTransaction` 内）：
admit 准入（:1504-1513）→ `mapEventData` → 记录创建 → `resolve` → 同步 computation → `afterDispatch` → 幂等回执 `dispatchIdempotency.finish`（:1584-1594，**随事实同事务提交**）。任一步失败 → 整体回滚 → `result.error`。

**阶段 P —— 提交后义务**（commit 之后、事务之外）：
`postCommit` 钩子 + `RecordMutationSideEffect`（:1360-1379；BT 内推迟到 owned COMMIT 之后 :1241-1254、:1365-1370）。失败被逐项捕获为 `SideEffectError` 写入 `result.sideEffects[name].error`（`runRecordChangeSideEffects` :1645-1682；postCommit 失败写 `sideEffects.__postCommit.error`，:1626-1642），**不设置 `result.error`、不回滚事实**。

两个既定政策：

1. **幂等重放跳过 P**：`outcome === 'replayed'` 时直接返回（:1361-1364，源码注释 "P (postCommit + mutation side effects): never on idempotent replay"）。
2. **应用层去重惯用法**：EventSource 在 `admit` 里对重复业务键抛错 → 事务回滚 → `result.error` 携带该错误 → 调用方按错误类型识别"已生效"。

`RecordMutationSideEffect` 是框架官方指定的"事实提交后必须发生的非事实逻辑"挂点：外部调用、二级 dispatch、跨系统物化、通知。框架自己的文档示例也把它作为推荐路径。

## 2. 问题本质

### 2.1 不对称：事实 vs 提交后义务

| 维度 | 事实（阶段 A） | 提交后义务（阶段 P） |
|------|----------------|----------------------|
| 原子性 | 事务内，失败回滚 | 提交后执行，失败不回滚事实 |
| 失败上报 | `result.error`（一等、全框架一致） | `result.sideEffects[name].error`（要求调用方记得遍历 map，纯约定） |
| 去重 | EventSource 幂等回执 / admit 准入 | 无 |
| 上游重投的收敛 | `outcome: 'replayed'` 返回已归档结果 | replay 跳过 P；admit 去重抛错被调用方当"已成功" → **假成功** |
| 崩溃窗口 | 无（事务原子） | commit ↔ 执行 之间存在窗口，crash 后义务永久丢失且无痕迹 |
| 重执行 | 不需要（事实已持久） | **无任何原语** |

### 2.2 三个具体缺口

**G1 失败可见性不是一等语义。** `DispatchResponse.error`（:116-127）只覆盖阶段 A。P 阶段失败的正确消费方式是遍历 `result.sideEffects` 检查每个 entry——框架没有提供任何官方判别 helper、没有严格模式、测试面也没有覆盖失败契约（`tests/runtime/recordMutationSideEffect.spec.ts` 只覆盖 happy path）。结果是可以预测的：应用代码系统性地只检查 `result.error`，P 阶段失败静默丢失。

**G2 已提交事实的义务不可重执行。** 框架公开面上没有"对既有记录重跑阶段 P"的原语（`runRecordChangeSideEffects` 要求调用方持有含 `effects` 的 `DispatchResponse`，只有正常 dispatch 才有）。后果：

- P 失败后，调用方即使看见了（自己遍历 sideEffects）也无法重跑，只能重做整个业务事件；
- commit 后、P 前 crash，义务丢失且不可发现、不可恢复；
- 上游 at-least-once 投递（消息代理、outbox、重试调用方）重投同一事件时，无论走应用层 admit 去重（抛错→调用方视为已成功）还是框架幂等（`replayed`→跳过 P），**都无法触发义务重执行**——上游的 at-least-once 传不到 P 阶段。

**G3 完成状态本身不可查询。** 幂等回执在事实事务内落为 `succeeded`（:1584-1594），先于 P 执行。因此"事实已提交"与"事实已提交且义务已完成"在框架里是同一个状态、无法区分——G1/G2 的任何调用方侧修补都重建不出这个信息。

### 2.3 根因抽象

框架把事务边界定义为事实边界（正确的决定——外部调用不该在事实事务内），并给了义务一个官方挂点（提交后副作用），但没有给这个挂点配套的**完成语义**：完成判别（一等结果）、完成恢复（重执行）、完成事实（是否已跑过的持久判别）。相当于框架鼓励把重要逻辑挂在 P，却只给 P **at-most-once 执行 + 约定式可见性**，而事实本身享受去重 + 重放收敛 + 原子性的完整待遇。

应用侧因此被迫二选一：要么把义务塞回事实事务（违背阶段划分的初衷），要么自建对账/轮询/双写（框架明确反对的旁路）。两者都是表达力缺口的外溢。

## 3. 最小复现（纯框架构造）

```ts
// EventSource：entity X 带唯一业务键 key；admit 对重复 key 抛 DuplicateError（应用层去重惯用法）
// RecordMutationSideEffect S：record = X.create，content 抛错（模拟义务失败）

// 第一次 dispatch({ key: 'a' })
// 实际：X 已提交；result.error === undefined；result.sideEffects.S.error 是 SideEffectError；
//       只检查 result.error 的调用方认为成功 —— G1
// 第二次 dispatch({ key: 'a' })（上游 at-least-once 重投）
// 实际：admit 抛 DuplicateError → result.error 携带它；S 不再执行；
//       把 DuplicateError 当"已成功"的调用方返回成功 —— G2，义务永久丢失
// 全程：没有任何 API 能让 S 对已提交的 X 再执行一次
```

真实应用里的典型失败形态：上游是持久 outbox（事件已落库、投递成功才标记），P 失败但 `deliver` 判定成功 → outbox 标记已投递 → 业务镜像永久停在中间态；预算耗尽进死信表后也没有再执行路径。

## 4. 需求一览

| ID | 标题 | 优先级建议 | 一句话 |
|----|------|------------|--------|
| **FR-SE-01** | 副作用完成状态一等化 | P0 | "P 阶段是否全部成功"必须是 dispatch 结果中可编程判别的一等信息，而非调用方遍历约定 |
| **FR-SE-02** | 已提交事实的义务可重执行 | P0 | 对已提交的 create 型事实，官方原语可重跑其阶段 P，输入确定性重建，失败同形状上报 |
| **FR-SE-03** | 去重/重放路径的义务收敛 | P0 | 上游 at-least-once 重投时，调用方可表达"重投仍要求义务完成"；dedup 命中不再固化为假成功 |
| **FR-SE-04** | 义务完成可查询（完成回执） | P1 | "义务是否已跑过"成为可查询的持久事实，覆盖 commit↔P 崩溃窗口 |

FR-SE-01/02/03 相互配合构成最小闭环；FR-SE-04 是更强的完整形态，可作为二期。

## 5. 需求详述

### 5.1 FR-SE-01 — 完成状态一等化

- `DispatchResponse` 需要一个官方的完成判别（形态由设计定：一等布尔/枚举字段、官方 helper、或严格模式下的显式 outcome 扩展），语义为"P 阶段全部成功"或"存在失败 + 失败明细"。
- 必须覆盖 postCommit 失败（今日藏在 `sideEffects.__postCommit`）。
- 默认行为不破坏：不主动 throw、不改变现有调用方的返回值消费方式；严格性是选择加入。

### 5.2 FR-SE-03 — 去重/重放路径的义务收敛

两个去重路径都要有官方答案：

- **应用层 admit 去重**：调用方需要能区分"重复且义务已完成"与"重复但义务未完成/未知"，并在后者时触发重执行（配合 FR-SE-02），而不是把重复错误一律折叠为成功。
- **框架幂等 replay**（`outcome: 'replayed'` 跳过 P）：重放 dispatch 对 P 的语义需要显式化——要么官方声明"replay 不含义务，义务完成走 FR-SE-02"，要么提供要求义务收敛的重放入口。当前状态是最差的组合：文档化跳过 + 无替代路径。

### 5.3 FR-SE-02 — 义务重执行原语

期望语义（须逐一定义并测试）：

1. **输入重建确定性**：重执行拿到的 mutation event 与首次执行同构（create 型：记录从 storage 全属性加载）。
2. **重跑 = 全量重跑**：对该记录名上注册的全部副作用整体重跑；**副作用幂等是框架合同**（与今日"P 失败不重试、调用方重发整个事件"的隐含要求一致，只是把它显性化）。
3. **失败上报同形状**：逐副作用错误进 `sideEffects`，不 throw、不改事实。
4. **进程局部性**：与今日一致，副作用在调用方持有的 Controller 实例上执行（`recordNameToSideEffects` 是实例级注册表）；跨进程装配差异是应用责任，框架文档写明。
5. **支持范围显式化**：create 型是良定义子集（append-only 事实日志、事件实体）。update 型需要 `oldRecord`，storage 无历史不可恢复——要么明确不支持，要么引入历史，须作为设计决策写清。

### 5.4 FR-SE-04 — 义务完成回执（P1，完整形态）

把"义务已对某次提交执行过（及结果）"落为框架管理的持久标记，使 G3 的状态合并被拆开：事实回执（已有，幂等表）与义务回执分离。收益：崩溃窗口可发现（未完成的义务可查询）、FR-SE-02 的重执行可跳过已成功项（细粒度收敛）、FR-SE-03 的"重复且义务已完成"判别有据。边界：回执只是**完成事实**，不是调度器——重试策略、退避、投递编排仍归应用（见非目标）。

## 6. 约束与非目标

- **不改事实事务模型**：P 在提交后执行的时序、失败不回滚事实，都是正确决定，保持不变。
- **框架不做出站调度**：不内置重试/退避/outbox/死信调度。投递策略归应用；框架补的是完成语义（判别 + 重执行 + 可选回执）。FR-SE-04 的回执是状态不是调度器。
- **副作用保持非事务al**：不试图把 P 纳入事实事务或提供补偿事务框架。
- **向后兼容**：现有"只检查 result.error"的调用方行为不变；新语义一律选择加入或独立入口。
- **单一真相**：完成语义与幂等 `outcome` 语义必须一致叙述，不产生第二套"成功"定义。

## 7. 候选方向（非约束性，供设计讨论）

- **方向 A：显式重执行 API**（Controller 方法，按记录重跑 create 副作用）+ FR-SE-01 的结果字段。
  正交、实现直接；但可见性仍偏约定、调用方要自己把"判别→重执行→重投收敛"串起来，每个应用重写一遍编排。
- **方向 B：dispatch 级义务完成合同**。调用方在 dispatch 上声明义务要求（如 `dispatch(source, args, { effects: 'require' })`）；框架在首次执行与去重/重放路径上统一执行"义务完成"逻辑：未完成则执行（或重执行）P，结果以一等完成状态返回；admit 去重命中时不再把"重复"直接折叠为成功，而是折叠为"义务收敛请求"。
  单点声明、编排逻辑进框架、应用零手工串联；需精确定义与 admit 抛错、`outcome: 'replayed'`、BT 推迟执行的合成规则，是这个方向的主要设计成本。
- **方向 C：义务完成回执 + 官方查询/重放入口**（FR-SE-04 的完整形态，内含 A 或 B）。
  覆盖崩溃窗口与细粒度收敛；概念与存储成本最高，应分期。

评价标准：①"上游 at-least-once → 义务 at-least-once"能否成为**官方模式**而非应用手工编排；②API/概念面最小；③与幂等 outcome 的一致性（无第二真相）；④向后兼容；⑤失败判别、重执行、崩溃窗口三者各有确定性测试。

## 8. 验收标准（任一方案应能证明）

1. 副作用失败 → 调用方以官方判别（非遍历约定）得知"未完成"，且能拿到失败明细。
2. 上游重投同一事件（admit 去重命中或幂等 replay）→ 义务被重执行直至成功；幂等副作用吸收重复执行（含"部分成功后重跑"场景）。
3. commit 成功但 P 未执行（进程崩溃模拟）→ 存在官方自愈路径（方向 C 下可查询未完成项）。
4. 回归：正常 dispatch、幂等 replay 默认跳过 P、BT 推迟执行、postCommit 语义全部不破坏；现有测试面无新增失败。
5. 框架仓库补齐 P 阶段失败/重执行的测试契约（今日 happy-path-only）。

---

*来源动机：一个应用仓库把权威事件消费挂在 `RecordMutationSideEffect` 上、上游为持久 outbox 时，复现了上述全部缺口（失败不可见、重投假成功、死信无再执行路径）。复现实验与源码行号核对于 interaqt `aa7d1c7`（v4.8.0）。*
