# interaqt 响应式范式能力缺口需求清单（2026-08-29）

## 1. 背景与阅读说明

- **来源**：本清单提炼自一份对某大型生产应用（基于 interaqt 4.8 构建）的独立源码评审。原评审中的业务名称、模块名、文件路径均已移除，只保留可泛化的场景描述；条目编号 GAP-1 至 GAP-12 与来源评审的 P-1 至 P-12 一一对应。
- **定性**：这不是应用层的错误清单。来源应用对以下每一个场景都建立了工程质量尚可的绕行结构，绕行本身大多是合理的。值得框架吸收的信息是"为什么必须绕"——即响应式范式在哪些场景下**难以表达需求**，或**表达得了但代价不成比例**。
- **参照模型**：interaqt 的理想形态是全声明式——开发者声明实体（Entity）、关系（Relation）、交互（Interaction）与派生计算（Computation）；用户动作产生不可变的交互事件（InteractionEvent），框架据此自动重算全部派生状态。可以类比电子表格：业务规则是公式，框架负责在输入变化时自动重算。下述缺口均以此模型为参照。
- **版本基准**：以 interaqt 4.8 的公开行为为基准。若后续版本已提供对应能力，以框架现状为准，条目可直接关闭。
- **术语约定**：专业术语在首次出现处给出简短定义，全文不使用任何应用内部代号。

## 3. 缺口详述

### GAP-1 身份自举与按自然键的幂等创建

**场景。** 用户注册、邮箱验证码签发、第三方合作方的自动开通等系统入口，发生在"操作主体尚不存在"的时刻——注册动作的产物才是主体本身，这是一个自举问题。同时，这类入口普遍要求按自然键（业务上天然唯一的标识，例如邮箱地址）的幂等创建：两个并发的相同请求只允许产生一条记录；在唯一约束竞争中失败的一方不应向调用者报错，而应读取胜出方创建的记录并继续后续流程。

**范式为何难以表达。** 交互事件模型预设"先有主体、后有事件"：每个 InteractionEvent 都携带发起人。框架既没有面向匿名或系统来源的事件原语，也没有"插入或收敛"（upsert，即记录存在则读取或更新、不存在则创建）的声明式原语。唯一约束冲突之后的裁决——读取胜出记录继续，还是失败退出——只能由应用层手写。

**应用层的典型绕行。** 在交互体系之外手写存储原语：按自然键条件创建，捕获唯一约束冲突，再按预设策略处理。这类代码绕过了事件轨迹，需要应用自行登记与测试。

**建议的框架能力。**
1. 匿名/系统事件源：允许在无主体上下文中产生合法的、可审计的事件。
2. 一等的 upsert-by-natural-key 原语：声明自然键与冲突策略（收敛 / 失败），由框架保证并发下恰好产生一条记录，且冲突方能拿到胜出记录。现有的 `Entity.identity` 类能力解决了"声明标识"这一半，冲突裁决仍是空白。

### GAP-2 存量数据列升级为派生列（计算的收养语义）

**场景。** 一个已上线、含真实生产数据的普通列（例如媒体文件的时长），团队希望将其升级为响应式派生列，让框架此后自动维护。

**范式为何难以表达。** 属性一旦挂上 computation，框架即全面接管该列，包括用计算的初始状态覆盖现有值。对全新列无害；对存量列等于数据破坏。因此"普通列演进为派生列"的路径事实上不存在。

**应用层的典型绕行。** 存量列永远留在响应式体系之外，由官方命令式边界（例如事件源的 resolve 回调，在分发事务内执行）直写维护。留在范式之外的命令式写点会随系统年龄持续增多。

**建议的框架能力。** computation 的"收养模式"（adoption）：接管一个属性时，将既有存量值视为初始状态，只对此后的输入变化负责重算。配套提供从直写列到派生列的迁移校验工具，例如可选执行的"存量值与派生函数回放结果的一致性检查"。

### GAP-3 按属性分组的聚合

**场景。** 多租户系统的核心聚合几乎都以某个属性为分组键：每个账户的余额、每个工作区的配额与席位数、每个租户的存储用量——即 SQL 中 `SUM(...) GROUP BY scope_id` 的形态。

**范式为何难以表达。** 内建的 Count / Summation 只有两种形态：沿 Relation 路径聚合到关联记录上，或对整张实体表做全局聚合。不存在"按属性值分组"的聚合。当实体之间未建立 Relation 时（见 GAP-9），前一种形态也不可用。

**应用层的典型绕行及其脆弱性。** 为每个聚合值手工搭建 StateMachine：枚举所有会影响该聚合的交互作为状态转移触发，导出一份"合法写入来源清单"供测试比对，并在并发敏感处（例如余额扣减）自行加数据库行级锁防止超额扣减。脆弱性是结构性的：每新增一个影响聚合的交互，必须人工同步状态机的转移表；框架不保证这份枚举的完整性，遗漏的表现是聚合值静默过期，而不是报错。

**建议的框架能力。** 一等的分组聚合 computation：声明源实体、分组属性、聚合函数与增量维护策略，由框架保证所有写路径都被纳入，正确性不再依赖人工枚举。来源评审将此项列为对生产应用价值最高的一项扩展；余额、配额、席位数、存储用量属于同一形态的普遍需求。

### GAP-4 物化视图 / 可重建投影原语

**场景。** 审计型与协作型系统常见的读模型需求：事实以只追加方式存储，并形成修订链（同一业务对象的历次修订构成一条链）；读取时需要——
1. 从每条修订链折叠出当前生效版本；
2. 保证一次读取内部的快照一致性，不因并发写读到半新半旧的数据；
3. 维护"当前活动事实"的指针索引，使读取代价与活动事实数量成正比，而不是与全部历史成正比。

**范式为何难以表达。** computation 由单条写事件驱动，无法表达"按键批量重建""从提交后快照取输入""跨行失效"这类语义（Transform 亦只被写事件驱动）；派生结果若建模为实体，会被吸入响应式依赖图，带来非预期重算与依赖环风险；框架也没有"投影与源数据读取等价"这一契约的安放位置。性能动机同样真实：没有指针索引时，每次读取都要对全部历史事实做一次折叠。

**应用层的典型绕行。** 来源应用以约一千行代码手工实现了完整读模型：写路径遵循"加性写入、推进版本水位、再做减性收缩"的三阶段纪律；读路径在读取前后各读一次单调递增的版本水位，两次一致才确认未发生撕裂；退化路径为全表折叠。

**建议的框架能力。** 框架级物化视图原语：声明失效键（哪些源变更使哪些投影键失效）、派生函数与幂等重建协议；投影显式排除在响应式依赖图之外；并提供读取等价性的测试契约。

### GAP-5 读触发的惰性刷新（拉模型）

**场景。** 外部长时任务的状态查询：客户端轮询 GET；期望语义是"若缓存数据超过 N 秒，则在读取路径上向外部服务商做一轮拉取并更新缓存；拉取失败不影响本次响应，返回缓存值；权威收敛仍由后台重试机制负责"。

**范式为何难以表达。** 响应式是推模型：只有写事件驱动重算，不存在"因读取而触发一轮收敛"的原语。节流、并发合并（single-flight：同一时刻至多一个刷新请求在途，其余复用其结果）、失败回退这类惰性派生语义在框架内无处安放。

**建议的框架能力。** 惰性派生原语：为派生数据声明过期窗口、刷新函数、并发合并策略与失败回退语义，由读取路径自动执行。

### GAP-6 观测型属性与事件写放大

**场景。** "API 密钥的最近使用时间""访问计数""消费游标"这类高频更新、纯观测、没有任何业务派生依赖它们的属性。

**代价何在。** 正统路径要求每次更新都经交互产生一条永久事件记录。以 API 网关为例：每处理一个请求，就要为维护一个时间戳追加一条事件——持久写入量与请求流量同速增长，与该字段的价值完全不成比例。这种现象称为写放大：为记录一次微小更新而产生的持久写入量远超更新本身。

**应用层的典型绕行。** 节流直写数据库，并以静态检查保证没有任何 computation 依赖该列，从而证明绕过事件系统不破坏一致性。每新增一个此类字段，都要重复这套登记与检查。

**建议的框架能力。** 框架承认的"观测型属性"类别：声明为非事件化（更新不产生事件记录）、不可被任何 computation 依赖（框架静态拒绝此类依赖）、支持节流或合并写入。

### GAP-7 跨进程副作用投递

**场景。** 生产部署普遍是多进程：HTTP 服务进程、后台任务进程、智能体运行时进程各自加载同一套实体定义。进程 A 中产生的记录变更，需要触发注册在进程 B 的消费逻辑——例如后台进程完成任务后，触发面向用户的通知逻辑。

**范式为何难以表达。** computation 与记录变更副作用（RecordMutationSideEffect）只在发起分发的进程内执行；框架隐含单进程假设，跨进程投递没有原语。

**应用层的典型绕行。** 应用自建发件箱模式（outbox：把待投递事件作为数据行与业务写入放进同一个数据库事务，另由消费进程扫描并重放，实现至少一次投递），幂等去重由消费方自理。"哪个消费者必须部署在哪个进程"只有文档约定，没有静态检查；配置错误的表现是静默失败——事件被标记为已投递，但目标进程根本没有注册消费者。

**建议的框架能力。**
1. 框架级事件外发与订阅机制（内建 outbox 或等价物），提供跨进程至少一次投递的保证与幂等消费的钩子。
2. 消费者与进程的声明式注册表，可静态校验"每个必须完成的副作用，在其目标进程都有注册"。

### GAP-8 长时流程编排（Activity 抽象的代差）

**场景。** 真实的长时工作流需要：失败重试与退避、超时控制、外部回调（含签名校验）、按操作标识的幂等、多步补偿（saga：由一串本地事务与对应补偿动作组成的长事务模式）、供应商降级路由。

**现状证据。** 来源应用全库对框架的 Activity 抽象零使用；上述需求全部由自建的、基于 PostgreSQL 的持久化任务引擎加命令式编排门面承担，单个门面文件达数千行、编排十余个细粒度交互。这说明 Activity 当前的表达力与真实工作流之间存在代差——抽象存在，但生产场景无人能用。

**建议的框架决策（二选一，明确即可）。**
1. 演进 Activity：吸收持久执行语义——状态持久化、重试与超时、幂等重放、补偿、外部回调。
2. 正式废弃 Activity，把"响应式框架加外置编排引擎"确立为受支持的正统组合，并给出集成契约：事件如何进出编排引擎、事务边界如何划分。

最不利的状态是当前的悬置。

### GAP-9 Relation 采用激励不足（生态观察）

**场景。** 演进中的应用常以业务键属性（例如一个 `accountId` 字符串字段）而非 Relation 来关联实体，作为过渡状态。来源应用中体量最大的几个模块（实体数 12 至 22 不等）均为零 Relation。

**后果。** 范式最有价值的能力——沿关系路径的查询（attributeQuery）、按记录的关联聚合、级联权限——恰恰在最大的模块里全部不可用，查询退化为手写的逐条查找链。并且存在收益递减循环：框架缺少分组聚合（GAP-3）与高效的按业务键连接，导致回填 Relation 的回报不足；不回填，范式在新模块中的占有率就持续下降。

**建议的框架能力。**
1. 落实 GAP-3（分组聚合）。
2. 提供高效的按业务键查询与连接支持。
3. 提供"业务键属性迁移为 Relation"的工具链：生成回填脚本、校验双向一致性，降低回填成本，恢复采用激励。

### GAP-10 权限条件的重复查询开销

**场景。** 每次交互分发都要评估一组权限条件（Condition）；每个条件是独立的异步函数，内部各自发起一到三次存储查询；条件经布尔组合器（BoolExp）组合后，仍然各自独立执行。

**代价何在。** 同一次分发内，多个条件对相同数据（例如"当前会话记录""目标节点及其所属工作区"）重复查询，没有任何共享缓存或预取。对高频交互（消息发送、心跳类），这构成每次调用固定的多次数据库往返，随流量线性放大。

**建议的框架能力。**
1. 分发级共享查询上下文：同一次分发内，对相同的存储读取做记忆化（memoization，即首次执行后缓存结果供后续复用）。
2. 或者声明式数据范围权限：条件声明其所需的数据路径，框架统一预取后再评估各条件。

### GAP-11 事件日志的生命周期管理

**场景。** 范式的地基是只追加日志：交互事件表永久记录每一个用户动作；应用自建的任务生命周期事件表、对话消息历史表随业务高频增长。

**代价何在。** 框架现有的保留机制（`Entity.retention`）只适合一次性令牌这类小型 TTL 实体。对高增长事件表，框架没有任何归档、分层或清理机制；存储成本与查询性能的退化只是时间问题。这不能只归为应用架构问题——"事件不可变、永久追加"正是范式自身的要求，其存储后果理应由框架或平台层给出解决方案。

**建议的框架能力。** 事件日志的分层保留策略：热/冷/归档分层、按时间或水位触发的归档钩子，并明确归档之后框架各能力——事件重放、审计查询、副作用重跑——各自的保留边界。

### GAP-12 命令式写边界的可治理性

**场景。** 框架提供官方命令式边界（例如事件源的 resolve 回调，在分发事务内执行），应用在其中合法地直写事实列。随着此类写点增多，必须能回答"哪些实体的哪些列，允许在哪个边界被直写"。

**缺口。** 框架对此没有任何声明或校验机制，治理只能靠应用层自建注册表、契约测试与代码注释纪律。来源应用为多数直写面建立了"注册表即代码"的静态门禁，但评审发现的唯一实质违规恰恰出现在一个未登记的缝隙上——说明纯应用层的黑名单式治理必然存在漏网。

**建议的框架能力。** 命令式写面的声明式登记：事件源或自定义边界在定义处声明其可写的实体与属性集合，框架在启动时或静态检查中拒绝未声明的直写。应用层治理由此从"黑名单巡逻"升级为"白名单闸门"。

## 4. 推进建议

- 建议逐项先做"框架应否支持"的判定，再设计 API 形态。
- 改动面预估：GAP-3、GAP-4、GAP-7 触及存储与运行时核心，改动面大；GAP-2、GAP-5、GAP-6、GAP-10 相对局部；GAP-8 首先是一个方向决策；GAP-9 是采用动力学观察，其解除依赖 GAP-3 的落地；GAP-11 可与平台层分工；GAP-12 是独立的治理机制，可单独推进。
- 优先级：来源评审仅对 GAP-3 给出明确排序（最高优先级，理由是同形态需求在生产应用中最普遍、且现有绕行的脆弱性由人工纪律承担）。其余条目未排序，建议按改动面与收益自行评估。
