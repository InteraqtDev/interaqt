# 应用键的跨副本原子占有

> 面向 interaqt 框架本身的问题陈述。描述缺口、目标和边界。唯一的架构前提：应用数据变化必须经框架唯一写入口——声明 + `Controller.dispatch`（不得新增与 `dispatch` 平行的占有写 API）。除此之外本文不预设任何声明面、机制或结果通道；一切由后续设计求证后裁定，只保留一个方案。

与相邻问题的边界：

| 已有 / 另文 | 解决什么 | 本文不重复 |
|-------------|----------|------------|
| Interaction `idempotency` + `_DispatchIdempotency_` | 同一次 `dispatch` 的首次 / 回放 | 应用自己的键（握手口令、兑换码、跨 API 票据），不是 interaction 幂等键 |
| 按已有记录 `id` 或全局键的条件更新 / 行锁 | 行已经存在时的条件写入 | 行还不存在时，按应用键决定谁先登记 |
| `Entity.retention` / `maintainEntityRetention` | 已声明为 Entity 的有界保留 / TTL | 记录根本不在框架管理的持久模型里时，保留机制够不到 |
| 源图与滞后投影的读约定 | 两张可查询表如何列表、是否混读 | 那是应用读路径约定，不在本文 |

---

## 1. 问题

多个进程、多条数据库连接必须对下面这件事达成一致：

**这一枚由应用定义的键，现在是否已经被占有；若已被占有，载荷是什么；若尚未消费且尚未过期，能否由一方且仅由一方取出并标记为已用。**

权威只能落在**共享的持久存储**上。进程内的映射表在多副本下不是权威。

这类键的典型动机（不是要在本仓库实现的具体产品）：

- 握手一次性口令
- 兑换码 / 一次性票据
- 跨接口、跨请求的「这枚令牌只能被成功处理一次」

它们的身份是应用自己的复合键（例如命名空间 + 令牌标识），既不是框架为每条记录分配的 `id`，也不是某一次 Interaction dispatch 的幂等键。

### 1.1 需要能够被观察的行为

1. **先到者登记。** 同一应用键上，先成功的一方写入载荷并算占有成功；后到的一方得到稳定的「已被占用」，而不是把唯一约束异常、驱动错误或空结果当成业务语义。
2. **至多使用一次。** 未消费且未过期：返回载荷并标记已消费。已消费：稳定的「已使用」。已过期：稳定的「已过期」。这三种情况都是结果，不应当成未处理的程序故障。「结果」指调用方能经官方承诺的通道稳定地编程分支——响应数据、类型化拒绝、事件或查询约定均可，由设计裁定；不得要求捕获驱动异常或解析错误消息字符串。
3. **有界存活。** 过期或超额的行可以被官方维护步回收，业务默认路径不必手写删除循环。回收之后，同一键是否允许再次被占有，必须说清楚并且可测。
4. **留在框架的持久模型里。** 安装与迁移知道这张表；其余领域可以按框架常规方式查询；可以按已有保留机制回收。不得以「这是技术表」为由，把正式后端建成应用私有的 `CREATE TABLE` 加方言 SQL——那种表不进 schema / 迁移，不能挂 computation，也不能被其余领域当作普通记录看见。

### 1.2 失败形态

若上述行为无法在框架管理的记录上表达，应用会自己建表并用方言 SQL 完成「插入成功者赢」和「未消费才更新」。于是出现**第二套实体运行时**：形状像记录，但不参与框架的 schema、迁移、查询、保留和派生。

框架已经为**自己的**键空间维护过内部账本（例如 dispatch 幂等、序号）。那只能证明「按键原子占有」在存储层可行，不能证明应用键已经有一条官方、可见、可迁移的路径。

### 1.3 与现成能力的表面关系（供求证）

下列能力各自覆盖一部分。它们是否已经构成完整官方路径，必须在当前主干上用源码和实验核对，不得预先当作已解决或未解决：

- 唯一约束：能阻止同一键出现两行；冲突时调用方看到的是什么。
- 按 `id` 或全局键的条件更新 / 行锁：行必须已经存在时能做什么；行尚不存在时能做什么。
- 全局字典：是否有按命名空间分开的行、一次性消费、行级过期。
- dispatch 幂等账本：键空间绑在哪里；表是否进入应用迁移签名；能否当普通记录查询和保留。
- 实体保留：对已经是框架实体的行如何回收；对框架外的表是否可见。
- Interaction 准入：`Condition.locks` / `AdmissionSnapshot` / `InteractionGuardError.code` 类型化拒绝在并发 check-then-act 下覆盖什么；对尚不存在的行能做什么。
- mutation events：`DispatchResponse.effects` 与 `storage.listen` 能让调用方和其它领域观察到什么；缺什么。

## 2. 需求

在框架内提供一条可文档化的官方路径，使应用键上的跨副本先到者登记、一次性消费和有界存活，落在框架管理的记录上，并且结果稳定可测。

完成态看第 1.1 节四条行为是否成立，以及第 4 节验收能否区分对错实现。官方写路径必须是声明 + `Controller.dispatch`。由哪些声明概念构成路径（组合既有概念、扩展既有概念、或引入新的一般概念）、如何按应用键定位记录、调用方经什么通道观察结果，全部由设计求证后裁定，本文不预设其中任何一项。

下列**不得单独当作完成**：

- 只把行放进某张表，却仍用唯一约束异常冒充「已被占用」。
- 只能在已有 `id` 的行上做条件更新，却不能按应用键决定谁先登记。
- 只服务 Interaction dispatch 的幂等键。
- 生产路径把进程内映射当作多副本权威。
- 与 `Controller.dispatch` 平行的占有写 API（例如 `claim` / `consume`）冒充声明式官方路径。

## 3. 非目标

- 不内置分布式锁服务、租约续约协议或时钟同步算法。存活时间以存储时间为准，并在文档中写清。
- 不重做 Interaction dispatch 幂等。
- 不重做实体保留机制本身；本问题的有界存活应能复用已有官方维护步，而不是再做一套平行回收。
- 不预设官方路径由哪些声明概念构成；组合既有概念、扩展既有概念或引入新的一般概念均可（新概念的一般性论证要求见任务文档）。不得新增与 `dispatch` 平行的占有写 API。引擎内部可使用 SAVEPOINT 与行锁等机制，但不得上升为应用教义。结果必须仍是框架管理的行。
- 不把源图与滞后投影如何列表、是否在读路径上合并纳入本文（应用读约定，另文 / 非本任务）。
- 不在本仓库改造某个具体业务的私有令牌表。
- 不实施提交后副作用是否跑完（相邻问题：义务完成 ≠ 谁占有了哪一枚键）。

## 4. 验收时必须能区分的行为

- **并发先到者（真实 PostgreSQL）：** 同一应用键并发经官方路径登记，恰好一方成功并写入载荷，另一方得到稳定的已占用；无两行、无两份载荷生效。须同时覆盖两种拓扑：两条独立连接、各自独立 Controller（跨副本）；以及同一进程同一 Controller 上的并发 `dispatch`（连接池并发）。单连接或仅内存库不得单独充当并发完成证明。
- **一次性消费：** 登记成功后，一方经官方路径核销取出载荷，另一方得到已使用；按声明过期后，核销得到已过期。并发拓扑要求同上。
- **框架可见：** 关闭应用侧 DDL 后，安装 / 迁移仍能得到该记录的存储形状；迁移签名包含该形状。官方示例不得把应用 `CREATE TABLE` 当作占有后端。
- **保留：** 声明了 TTL 或数量上限后，官方维护步回收过期或超额行；未声明保留的其它实体不被误删。
