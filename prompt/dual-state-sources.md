# 双状态来源：重叠表示与框架外存储

> 面向 interaqt 框架本身的需求摘要。核心问题：**同一概念事实出现两份持久表示时，框架既不强制单一读权威，也不提供带冲突策略的官方合并；同时，一部分「看起来像实体」的记录可以完全活在 Entity / 迁移 / computation 之外。**
>
> 不绑定任何具体应用仓库。文中场景仅为通用动机说明。

与相邻需求的边界：

| 已有 / 另文 | 解决什么 | 本文不重复 |
|-------------|----------|------------|
| `Entity.retention` / `maintainEntityRetention` | 已声明为 Entity 的有界保留 / TTL | 保留策略本身；缺口是记录根本不是 Entity |
| `atomic.compareAndSet` | 已有行（或全局键）上的字段 CAS | 跨副本「按应用键首次占有 + 一次性消费 + TTL」的记录生命周期 |
| Interaction `idempotency` + `_DispatchIdempotency_` | dispatch 级首次 / 回放 | 业务令牌 / nonce，而非一次 interaction 的幂等键 |
| Transform 派生实体 | 从事件铸造 **canonical 形态** 的行 | 「可滞后、可丢弃的投影」以及「投影与源在读路径上如何共存」 |
| `prompt/post-commit-side-effect-delivery-guarantees.md` | 提交后义务的完成语义 | 状态表示的权威个数，不是副作用是否跑完 |

---

## 1. 背景

响应式 ER 的默认假设是：

1. **持久形状只有 Entity / Relation**（外加框架自管的内部表）。
2. **同一业务事实只有一份权威**；其它形状若存在，应是同一 `InteractionEvent` 上的另一条 Transform——两份投影、一个权威、读路径无需合并。
3. **读**走 `storage.find` / 关系路径 / nested `attributeQuery`，得到的就是那份权威（或其声明式派生）。

真实应用会反复碰到两类压力，把上述假设撕开：

**压力 A — 派生视图不完整。** 搜索索引、物化读模型、按 revision 缓存的图投影，相对源图（引用边 + 源实体）经常是滞后或子集。读方为了「现在就能列出」，把投影行与源图行在应用层做并集，再用一个不完整的去重键压成「同一条」。

**压力 B — 需要跨副本原子占有。** 一次性令牌、握手 nonce、lease 的 first-wins claim（`INSERT` 成功者赢，或 `UPDATE … WHERE consumed_at IS NULL`）在多进程下必须落在共享存储上。进程内 `Map` 不是权威。若 Entity + UniqueConstraint + dispatch 表达不了「按应用键原子占有且可一次性消费」，应用就会 `CREATE TABLE` + 方言 SQL，造出框架看不见的第二套实体。

两条看起来不像一类 bug，但失败形态同构：**调用方同时面对两份状态，且没有一等的权威 / 完整度 / 冲突合同。**

---

## 2. 问题本质

### 2.1 形态 A：重叠表示，读时手工合并

```text
源图 S     ：权威边 / 权威实体（例如「对象被引用」）
投影 P     ：由异步或旁路物化的派生行（例如「可搜索的索引行」）
读路径     ：rows = P ∪ fallback(S)
去重       ：只按身份的一个子集（例如外部对象键）
冲突       ：P 与 S 上同名属性不一致时，由插入顺序决定胜负
```

这不是「两个 Transform 投影同一事件」（那是合法的双形状、单权威）。这是 **两套写入路径、两套行、读时当成同一条**。

具体缺口：

1. **没有完整度合同。** 框架不区分「P 是 S 的完备投影」与「P 是 S 的滞后子集」。读方无法声明「只读 P」「P 缺失则明确 stale」「禁止与 S 混成同一行类型」。
2. **没有官方 coalesce。** 并集 + 去重 + 字段级冲突策略（投影优先 / 源优先 / 不相交属性拼接 / 冲突即失败）全是应用私货。去重键比身份窄时，属性分叉被静默吞掉。
3. **投影行长得像 canonical 实体。** Transform 的产物与源实体在存储层没有标记差异；查询 API 不会拒绝「把投影当源、把源当投影」的混读。

可观察后果：同一对象在过滤、排序、展示字段上随「先扫到哪张表」而变；补全投影或回填源图会改变已发出去的读结果，且没有类型错误或约束失败。

### 2.2 形态 B：实体形状的框架外存储

```text
业务需要：跨副本、按 (namespace, tokenId) 原子 claim / consume / TTL
框架内  ：Entity + UniqueConstraint + dispatch 要么过重、要么没有
          「不存在则插入、已存在则拒绝；未消费则可一次性消费」的一等语义
应用侧  ：CREATE TABLE IF NOT EXISTS …; INSERT; UPDATE … WHERE consumed IS NULL
```

该表：

- **不进入** 应用 schema / 迁移签名（`install` / migrate 不知道它）；
- **不能挂** Property computation / Transform / StateMachine；
- **不能挂** 已交付的 `Entity.retention`（TTL 只能手写 `DELETE` 或永不回收）；
- **不能** 经 `storage.find`、权限、Relation 被其余领域看见。

它与 `_DispatchIdempotency_`、`_ScopedSequence_` 同形（内部键空间 + 原子占有），但后两者由框架拥有；应用级令牌被挤到方言 SQL。结果是 **第二套实体运行时**，只是教义上假装不存在。

### 2.3 根因抽象

框架把「Entity」既当作 **唯一持久概念**，又当作 **唯一权威概念**，却没有：

- 把「权威事实」与「可滞后派生」分成两种声明；
- 把「按应用键跨副本原子占有的短命记录」收进同一持久概念（从而享受迁移与 retention）。

缺这两档声明时，应用只能再造一份存储，然后在读路径或生命周期上自己当框架。

## 3. 需求一览

| ID | 标题 | 优先级建议 | 一句话 |
|----|------|------------|--------|
| **FR-DS-01** | 重叠表示的读合同 | P0 | 同一事实的源与派生若共存，读路径必须有声明式权威或带身份键 + 冲突策略的官方合并；禁止插入顺序决胜 |
| **FR-DS-02** | 框架内的原子占有记录 | P0 | 跨副本 first-wins claim / 一次性 consume / TTL 必须落在框架管理的记录上，参与迁移与保留，禁止应用 `CREATE TABLE` |

两条相互独立，可分期交付。只实现投影物化、却仍允许读路径无合同并集，**不算** FR-DS-01 完成。只把 SQL 换成 Entity、却没有原子 claim 语义，**不算** FR-DS-02 完成。

## 4. FR-DS-01 — 重叠表示的读合同

### 4.1 期望语义

须提供一条可文档化的官方路径（可组合，但必须能写进教义），使下面三者至少成立其一，且测试能区分：

1. **单一读权威。** 派生视图声明为源图的投影：要么完备（读只走 P），要么显式不完备（读走 S，或读 P 时带 stale / pending 状态，**不得**把 P 行与 S 行压成同一无标记列表）。
2. **官方 coalesce。** 查询原语接受：身份键集合、冲突策略（投影赢 / 源赢 / 仅拼接不相交字段 / 冲突失败）、以及「未出现在投影中的源行是否纳入」。结果行带上来源标记。去重键必须等于声明的身份；窄于身份的去重应被拒绝或成为显式、可测的策略。
3. **合法双形状模式（仅此一种）。** 同一 `InteractionEvent` 上两条 Transform 写出两种行，权威仍是该事件；读某一种形状时不回源合并。这是已有正确用法的教义化，不是新原语，但必须写清：**异步补全的索引行不属于这种模式。**

无论选哪条，下列行为必须从推荐用法中消失：

- 应用层 `concat` 两张表再 `Set(partialKey)`；
- 同名属性冲突时依赖数组顺序；
- 把滞后投影当成与源可互换的同一行类型。

### 4.2 非目标

- 不在本需求内规定搜索引擎、向量索引或外部只读副本（那是集成边界）。
- 不要求每一次派生都必须同步完备；允许滞后，但滞后必须是声明状态，而不是靠并集假装完备。
- 不把「物化图投影的增量维护算法」展开为本需求（那是更广的投影原语；本文只收 **共存时的读合同**）。
- 不禁止两个实体描述相关但不同的事实（订单 vs 发票）；禁止的是 **同一身份、同一事实、两份持久表示、无读合同**。

### 4.3 验收标准

- **冲突可测：** 构造源行与投影行共享身份键、某展示字段取值不同。无声明 coalesce 的混读要么无法通过官方 API 表达，要么按声明策略得到确定胜者，**不得**随查询顺序翻转。
- **完整度可测：** 仅存在源、尚无投影行时，官方读要么只返回源（并标记非投影），要么返回空 + stale，由声明决定；合同断言与声明一致。
- **合法双 Transform：** 同一事件两条 Transform 写出形状 A / 形状 B，分别查询得到各自全集，测试中 **禁止** 出现并集去重代码。
- 文档给出最小示例；反模式明确写出「读时手工并集 + 部分键去重」。

## 5. FR-DS-02 — 框架内的原子占有记录

### 5.1 期望语义

应用可声明一类记录（Entity 或与 `_DispatchIdempotency_` 同级的官方内部类型），满足：

1. **身份：** `(namespace, tokenId)`（或等价复合键）唯一。
2. **原子占有（claim）：** 跨进程、跨连接，先到者成功并写入 payload；后到者得到稳定的「已占用」结果，而非唯一约束异常冒充业务语义。
3. **一次性消费（consume）：** 未消费且未过期 → 返回 payload 并标记已消费；已消费 → 稳定的 already-used；过期 → 稳定的 expired（是否允许 TTL 后回收键再 claim，须文档化）。
4. **TTL / 保留：** 过期行可被 `Entity.retention`（或同等官方维护步）回收；业务默认路径无手写 `DELETE` 循环。
5. **框架可见：** 表由 schema install / migrate 创建与变更；禁止应用 `CREATE TABLE IF NOT EXISTS` 作为正式后端。可选：挂 computation（非必须，但不得因为「这是技术表」就被赶出 Entity 空间）。

`atomic.compareAndSet` 可作为实现零件（消费标记的 CAS），但 **不是** 本需求的完成形态：它不提供记录的创建 / 迁移 / TTL / 按应用键 first-wins insert。

Interaction 幂等账本 **不是** 本需求的完成形态：它绑定 dispatch 键，不能替代握手 nonce、兑换码、跨 API 的一次性票据。

### 5.2 非目标

- 不内置分布式锁服务、租约续约协议或时钟同步算法；TTL 与现有 retention 一样，以存储时间为准并在文档中写清。
- 不把进程内 `Map` 升格为多副本权威（测试内存后端可以，生产路径不行）。
- 不要求 claim 走完整 Interaction → Transform 栈（若过重，允许更窄的官方 API），但结果必须仍是框架管理的行。
- 不在本需求内重做 dispatch 幂等（已有 `outcome: 'applied' | 'replayed'`）。

### 5.3 验收标准

- **并发合同（真实 PostgreSQL，双连接）：** 同一 `(namespace, tokenId)` 并发 `claim` → 恰好一次成功，另一次 already-used；无重复 payload 生效。
- **consume：** claim 成功后一连接 consume 得 payload，另一连接 consume 得 already-used；过期后 consume 得 expired（按声明）。
- **schema：** 关闭应用侧 DDL 后，install / migrate 仍能得到该表；迁移签名包含其形状。负向：应用 `CREATE TABLE` 不得出现在官方示例中。
- **retention：** 声明 TTL 或 cap 后，维护步回收过期 / 超额行；未声明的其它 Entity 不被误删。
- PGLite / 单连接不得单独充当并发完成证明。

## 6. 与现有框架能力的关系

| 已有能力 | 关系 |
|----------|------|
| Transform 多实体派生 | FR-DS-01 的合法双形状路径；需在文档中与「异步索引 ∪ 源图」划清 |
| UniqueConstraint | 能兜底冲突，不能表达 claim 结果代数，也不能替代迁移可见性 |
| `atomic.compareAndSet` / `lockRecord` | FR-DS-02 的实现候选；今日不是按应用键 insert-or-claim 的一等 API |
| `_DispatchIdempotency_` | 证明框架已经为 **自己** 做过形态 B；应用级令牌应对齐同一可见性，而不是再抄一张私有表 |
| `Entity.retention` | FR-DS-02 的 TTL 应复用，而不是再做一套 GC |
| Dictionary | 全局 JSON KV，无 namespaced 行、无 consume-once、无行级 TTL |

---

## 7. 建议落地顺序

1. **FR-DS-02**：缺口最硬（方言 DDL + 无迁移），与已有内部账本 / CAS / retention 同族，合同边界清晰。
2. **FR-DS-01**：先把教义写死（合法双 Transform vs 非法读时并集），再决定是做官方 coalesce 还是做带完整度标记的投影读；避免只加物化缓存却仍允许无合同混读。
